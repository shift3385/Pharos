4. La forma de los datos, para acordar con «metrics-gate»

Todo vive en data del plan (JSON): sin migración ni número de migración que reservar, y se sincroniza como hoy. El texto criterion/metric de cada criterio se sigue escribiendo, generado desde la métrica, así que una app 0.3 que abra un plan 0.4 lo sigue evaluando por texto.

// src/modules/test-plan/model/types.ts (dueña: pista del plan)
export type MetricKind =
  | "executed" | "passRate" | "criticalDefects" | "coverage"   // las mide derive hoy
  | "defectDensity" | "escapedDefects" | "fixTime" | "reopenRate" | "flakyRate"; // DOC-06
// Contrato cerrado: metrics-gate repite estos literales en src/shared/metrics y en Rust
export type MetricOp = ">=" | ">" | "<=" | "<" | "=";
export type MetricUnit = "percent" | "count" | "per100cases" | "days" | "score";
export const METRIC_UNIT: Record<MetricKind, MetricUnit> = {
  executed: "percent", passRate: "percent", coverage: "percent", reopenRate: "percent", flakyRate: "percent",
  criticalDefects: "count", escapedDefects: "count",
  defectDensity: "per100cases",   // defectos por cada 100 casos ejecutados
  fixTime: "days",                // mediana de creación a «Corregido»
};

export interface PlanMetric {
  id: string;               // estable en el plan
  kind: MetricKind | null;  // null = métrica propia, se evalúa a mano
  name: string;             // la de una propia; "" en las del catálogo (etiqueta i18n)
  op: MetricOp;
  target: number;
  unit: MetricUnit;         // METRIC_UNIT[kind], bloqueada; libre solo si kind es null
  note?: string;
}

export interface ClosureCriterion {
  criterion: string;        // como hoy
  metric: string;           // como hoy; «≥ 95 %» generado si hay metricId
  metricId?: string;        // NUEVO: enlaza data.metrics[].id
  blocking?: boolean;       // NUEVO (DOC-02): true por defecto; false = orientativo
}

TestPlanData += {
  metrics?: PlanMetric[];
  entryCriteria?: string[]; suspensionCriteria?: string[]; resumptionCriteria?: string[];
  assumptions?: string[]; constraints?: string[];
  techniques?: string[];    // claves de catálogo + propias (ADR-0030)
  independence?: "author" | "peer" | "team" | "organization" | "external"; independenceNote?: string;
  training?: { need: string; when: string }[];
  estimation?: { technique: "ratio" | "extrapolation" | "wideband" | "threePoint" | "expert";
                 effort?: number; optimistic?: number; likely?: number; pessimistic?: number;
                 budget?: string; notes?: string };
  approval?: { by: string; byName: string; at: string; version: string } | null;  // PLN-07
  documentId?: string;      // PLN-04
}
Qué hace la pista del planTipos, asistente, import/export, i18n, y que el texto de cada criterio enlazado quede escrito. No toca derive, execution.ts del servidor, el cierre de ciclo ni el Inicio.

Una métrica kind: null se resuelve a mano en el cierre, como los criterios «manual» de hoy.

5. PLN-03 y PLN-04 en la misma pista

  • PLN-03 / NC-031: guardar sin cambios no llama al guardado (aviso «Sin cambios»); la versión sube solo si cambian título o contenido (no por cambiar el estado ni por aprobar); el escritorio no copia revisión si título y datos son iguales (test_plan.rs).
  • PLN-04: ID de documento por plan en «Identificación», editable, con valor por defecto TP-<prefijo del proyecto>-<6 hex del id> (p. ej. TP-PH-3F9A1C); el .xlsx lo escribe en C3 y el PDF en la cabecera.

  • PDF: secciones nuevas en el orden de los pasos; «Aprobado por / fecha» y el ID en la cabecera.
  • .xlsx: la plantilla (C3 y bloque de cabecera) gana «Aprobado por» y la fecha; los apartados nuevos van en una hoja «Estrategia» detrás de la del plan, con cabeceras es/en que el importador lee por nombre. Así la plantilla vieja y el importador de hoy siguen intactos.
