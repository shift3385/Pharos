Revisión de casos y baselines de suite

Un caso pasa de Borrador a En revisión y a Aprobado, y editarlo lo devuelve a Borrador. Una baseline congela un conjunto de casos en sus revisiones exactas y se puede comparar con el estado actual o con otra baseline. Sigue el patrón de la aprobación del plan (PLN-07, ADR-0040): confirmación, quién y cuándo, y editar quita la aprobación.

Reservas: ADR 0047, migración local 0042; la del servidor 0024 no hace falta (§7). Todavía no hay código.

1. El flujo

Los cuatro valores guardados no cambian (draft, reviewed, approved, obsolete), así que la app 0.4 sigue leyendo los datos. Cambia lo que muestra la 0.5: reviewed se lee «En revisión», es decir, pendiente de aprobación. El desplegable de estado desaparece del editor y cada paso es una acción con su regla.

  • Contenido es el título y lo que se ejecuta: descripción, precondiciones, pasos, resultado esperado, ejemplos, flujos, Gherkin, datos y requisitos enlazados. No lo son la prioridad, el estado de automatización, los campos propios ni la marca de revisión de la IA. Cambiarlos no quita la aprobación.
  • Guardar un caso aprobado con cambios de contenido sube la versión (1.2 → 1.3), como el plan.
  • Un archivo importado nunca trae aprobación: un caso «Aprobado» en el .xlsx o el .feature entra como Borrador.
  • Un caso que ya estaba aprobado antes de la 0.5 no tiene registro de quién lo aprobó. Se muestra «Aprobado (sin registro)» hasta la próxima aprobación.

Al abrir un caso «En revisión» se ve quién lo envió, su nota, y qué cambió desde la última versión aprobada. El cambio sale de las revisiones que ya se guardan, con el mismo comparador que las baselines (§6). «Aprobar versión N» pide confirmación. «Devolver» exige un comentario.

5. Crear una baseline de suite

Desde «Baselines» en la lista de casos (también desde la selección). Una baseline guarda, para cada caso, el ID, la revisión exacta y su estado en ese momento. No se edita ni se borra: para cambiarla se crea otra, como pide ISTQB para una línea base bajo control de cambios.

7. Datos, servidor y sincronización

En el caso (sin migración)

Como data.approval del plan, viaja con el caso y se sincroniza como el resto de su contenido.

data.review = {            // ciclo en curso o último devuelto
  state: "pending" | "returned",
  sentBy, sentByName, sentAt,
  revision, version, note?,
  returnedBy?, returnedByName?,
  returnedAt?, comment?
}
data.approval = {
  by, byName, at,
  version, revision,
  selfApproved: boolean
}

Baselines (migración local 0042)

case_baselines(
  id, project_id, name, description,
  scope_label, approved_only,
  created_by, created_at)
case_baseline_items(
  baseline_id, case_id, scenario_id,
  revision, status, title,
  PRIMARY KEY(baseline_id, case_id))

El contenido se lee de test_case_revisions, que ya existe y ya se sincroniza (DAT-02). Congelar es guardar (caso, revisión), igual que un ciclo congela la revisión de sus ítems.

  • Las reglas se aplican en el núcleo, no solo en la pantalla. El guardado normal ya no puede poner reviewed ni approved: lo hacen comandos propios (test_case_review en Rust y POST /api/test-cases/:id/review en la web) con send | approve | return | obsolete | reactivate. El servidor usa la cuenta autenticada, no un nombre enviado por el cliente. Un guardado que cambia el contenido de un caso en revisión o aprobado lo devuelve a Borrador en el propio núcleo, también si viene del import, de la IA o del CLI.
  • Servidor: la baseline se guarda como documento de solo-añadir (tx.append("case_baseline", …)) en la tabla de documentos que ya existe, así que la migración 0024 del servidor no hace falta y queda libre. Rutas: GET/POST /api/case-baselines, GET /api/case-baselines/:id y GET /api/case-baselines/compare?from=&to=.
  • Sincronización de baselines (punto con W): para que la baseline creada en el escritorio llegue a la web hay que registrar case_baseline como entidad de solo-añadir: una entrada en sync_class.rs, una línea en sync.schemas.ts del servidor y subir APPLIED_SET_VERSION. Es núcleo de sync, que es de W. Propuesta: lo añado yo en un commit aparte y W hace rebase, o se deja para la ola 2 y hasta entonces las baselines del escritorio son locales.
  • Compatibilidad (VERSIONING §6.5): no cambia ningún valor guardado. La app 0.4 ve «Revisado» donde la 0.5 dice «En revisión» e ignora data.review y data.approval. Contra un servidor 0.5 la 0.4 está en solo lectura, así que no puede saltarse el flujo.

8. Las dos costuras para otras pistas

Quién puede aprobar (para W)

// src/modules/test-cases/review/approver.ts
export interface ApprovalRequest {
  workspaceId: string;
  projectId: string;
  caseId: string;
  authorId: string;    // created_by del caso
  approverId: string;  // cuenta que aprueba
}
export type ApprovalVerdict =
  | { ok: true; selfApproval: boolean }
  | { ok: false; reason: "author" | "role" | "notMember" };
export interface ApproverCheck {
  canApprove(req: ApprovalRequest): Promise<ApprovalVerdict>;
}
// Por defecto, hasta que lleguen los roles:
// «otra persona que no sea el autor»; con un
// solo miembro, autoaprobación registrada.
export function otherThanAuthor(
  memberCount: (workspaceId: string) => Promise<number>,
): ApproverCheck;
export function setApproverCheck(check: ApproverCheck): void;

La misma forma en el servidor (server/src/modules/domain/case-review.ts, con la transacción) y en Rust (trait ApproverCheck en case_review.rs), porque la regla tiene que aplicarse donde se escribe. Hasta W, memberCount devuelve 1. W conecta su versión: rol Test Manager o Test Analyst y distinto del autor, y devuelve "role" si la cuenta no tiene ese rol.

Eventos para notificaciones (para R)

// src/modules/test-cases/model/events.ts
export const CASE_REVIEW_EVENT = "pharos:case-review";
export interface CaseReviewEvent {
  kind: "sent" | "approved" | "returned";
  caseId: string;
  scenarioId: string;   // ATS-014
  title: string;
  projectId: string;
  authorId: string;
  actorId: string;
  actorName: string;
  at: string;           // ISO
  version: string;
  comment?: string;     // nota o motivo
  selfApproval?: boolean;
}
export function onCaseReview(
  listener: (e: CaseReviewEvent) => void,
): () => void;          // devuelve "darse de baja"

Se emite en el cliente después de que el núcleo acepta la transición. R se suscribe y decide a quién avisar. Si R necesita notificar a otra persona en otro equipo, el mismo objeto sirve de carga para su API del servidor; no envío nada al servidor por mi cuenta.

9. Alcance, pruebas y documentación

Entra

  • Flujo completo en escritorio y web, con las reglas en Rust y en el servidor.
  • Filtro «Por revisar», aviso «Devuelto», envío a revisión en lote.
  • Baselines: crear, ver de solo lectura, comparar con el estado actual o con otra.
  • «Aprobado por» y «autoaprobación» en el PDF del caso y en el historial. El .xlsx no cambia (sus celdas las lee la importación).
  • Pruebas: Rust (transiciones, editar quita la aprobación, autoaprobación, baseline congelada aunque el caso cambie), servidor (las mismas, más un autor que intenta aprobar con dos miembros simulados), Vitest de UI y a11y, y un E2E del recorrido.
  • Docs en el mismo cambio: ADR-0047, fila de ROADMAP §5, changes/, manual (capítulo de casos) y glosario («baseline»).

No entra

  • Roles reales: la comprobación de W llega en la ola 2.
  • Varios revisores o un mínimo de aprobaciones: el usuario aprobó que basta uno.
  • Exportar una baseline o su comparación a .xlsx o PDF: se puede pedir aparte.
  • Que un ciclo se cree desde una baseline: tiene sentido, pero es trabajo de ciclos.
  • Notificaciones: las pinta R a partir del evento.

10. Lo que necesito que decida el usuario

1. ¿«Revisado» pasa a llamarse «En revisión»?

Guardar un valor nuevo (in_review) rompe la lectura de la app 0.4 y deja reviewed sin sentido. Reutilizar reviewed con otra etiqueta no cambia los datos.

Recomendación: reutilizar reviewed con la etiqueta «En revisión». Los casos que hoy están en «Revisado» quedan pendientes de aprobación.

2. ¿Editar un caso «En revisión» lo devuelve a Borrador?

Si no lo hace, alguien podría aprobar algo distinto de lo que se envió.

Recomendación: sí. Cambiar el contenido de un caso en revisión o aprobado lo devuelve a Borrador.

3. ¿La baseline incluye solo casos aprobados?

Recomendación: la casilla «Solo los casos aprobados» viene marcada y se puede desmarcar, avisando de cuántos se quedan fuera.

4. ¿Las baselines se sincronizan ya, en la ola 1?

Hace falta una entrada en el núcleo de sync (§7), que es de W.

Recomendación: sí, en un commit aparte y pequeño, avisando a W. La alternativa es que sean locales hasta la ola 2.
